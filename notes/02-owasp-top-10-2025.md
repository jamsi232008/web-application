# 2. OWASP Top 10 (2025) Analysis

The OWASP Top 10 is an awareness document listing the most critical web application security risks. The 2025 edition (the eighth edition, announced November 2025 and finalised in January 2026) added two new categories, merged SSRF into Broken Access Control, and moved Security Misconfiguration up to second place. Each category groups many related weaknesses (CWEs), so it is a guide for priorities rather than a complete testing checklist.

## 2.1 The list at a glance

| Rank | Category | Change from 2021 |
|---|---|---|
| A01 | Broken Access Control | Still #1; SSRF merged in |
| A02 | Security Misconfiguration | Up from #5 |
| A03 | Software Supply Chain Failures | New focus; expands "Vulnerable and Outdated Components" |
| A04 | Cryptographic Failures | Down from #2 |
| A05 | Injection | Down from #3 |
| A06 | Insecure Design | Down from #4 |
| A07 | Authentication Failures | Renamed (was Identification and Authentication Failures) |
| A08 | Software or Data Integrity Failures | Renamed/refined |
| A09 | Security Logging & Alerting Failures | Renamed (was Logging and Monitoring Failures) |
| A10 | Mishandling of Exceptional Conditions | New |

XSS is covered under **A05 Injection** (client-side injection), alongside SQL, OS command and LDAP injection.

## 2.2 Category-by-category analysis

### A01: Broken Access Control

**What it is:** Users can act outside their intended permissions: viewing others' data, modifying records, or reaching admin functions. Server-Side Request Forgery (SSRF), where the server is tricked into fetching attacker-chosen URLs, is now part of this category.

**Typical causes:** missing server-side checks, trusting IDs in URLs or hidden fields, relying on client-side hiding of buttons, permissive CORS.

**Examples**
- **IDOR:** `GET /invoice?id=1042` returns another customer's invoice when the ID is changed to `1043`.
- **Privilege escalation:** an ordinary user opens `/admin/users` directly and it loads.
- **Forced browsing:** unlinked pages reachable by guessing the path.
- **SSRF:** an "import from URL" feature fetches `http://169.254.169.254/` (cloud metadata) for the attacker.

**How to test (authorised lab):** log in as two users, replay user A's requests with user B's session and IDs; try admin URLs as a normal user; change object IDs and HTTP methods.

**Prevention:** deny by default; enforce ownership checks on every request; centralise authorisation; use indirect or unguessable references; validate and allow-list outbound URLs and block internal ranges for SSRF; log access failures.

---

### A02: Security Misconfiguration

**What it is:** Insecure defaults, incomplete setups, open cloud storage, verbose errors, unnecessary features or missing hardening.

**Examples:** default admin credentials, directory listing enabled, debug mode on in production, stack traces shown to users, missing security headers, overly permissive cloud bucket policies, unnecessary ports and services.

**Test:** review response headers, probe for default pages and credentials in the lab, check error handling and exposed config files, run ZAP/Nikto baseline scans.

**Prevention:** repeatable hardened builds, remove unused components, disable debug, set security headers, least-privilege cloud permissions, configuration review in CI, separate environments.

---

### A03: Software Supply Chain Failures

**What it is:** Weaknesses in the dependencies, build tools, update mechanisms and distribution channels software relies on, including outdated libraries and compromised packages.

**Examples:** an application using a library with a known CVE; a malicious look-alike package installed by typo; a compromised CI pipeline or build plugin; unsigned updates.

**Test:** inventory dependencies (SBOM), run `npm audit`, `pip-audit`, OWASP Dependency-Check, or Trivy; check lockfiles and pinned versions.

**Prevention:** maintain an SBOM, pin and verify dependencies, scan continuously, use trusted registries, sign artifacts, protect CI/CD credentials, remove unused packages.

---

### A04: Cryptographic Failures

**What it is:** Sensitive data is exposed because encryption is missing, weak or misused.

**Examples:** HTTP instead of HTTPS, passwords stored with MD5 or unsalted SHA-1, hard-coded keys, outdated TLS versions, predictable tokens, sensitive data in logs or URLs.

**Test:** inspect TLS configuration (for example `testssl.sh` or `nmap --script ssl-enum-ciphers`), look for cleartext credentials in Wireshark, review how passwords and tokens are generated and stored.

**Prevention:** TLS 1.2+ everywhere with HSTS; strong modern algorithms (AES-GCM, Argon2id/bcrypt for passwords); proper key management and rotation; do not store sensitive data you do not need; secure random generators.

---

### A05: Injection (includes XSS)

**What it is:** Untrusted data is sent to an interpreter as part of a command or query, changing its meaning.

| Type | Interpreter | Example |
|---|---|---|
| SQL injection | Database | `' OR '1'='1` in a login field changes the query logic |
| Cross-Site Scripting (XSS) | Browser | `<script>` injected into a page that reflects or stores input |
| OS command injection | Shell | Input appended to a `ping` command |
| NoSQL, LDAP, template injection | Respective engines | Operators or expressions inserted in input |

**XSS variants:** *Reflected* (payload in the request, echoed back), *Stored* (saved in the database and shown to other users), *DOM-based* (client-side script writes untrusted data into the page).

**Test (lab only):** submit harmless markers such as a single quote or `<b>test</b>` and observe errors or unencoded output; ZAP/Burp scanners and manual Repeater tests confirm.

**Prevention:** parameterised queries or ORMs; allow-list input validation; context-aware output encoding and auto-escaping templates; Content-Security-Policy; avoid `eval` and `innerHTML` with untrusted data; least-privilege database accounts; never build shell commands from user input.

---

### A06: Insecure Design

**What it is:** Flaws in the design itself that no implementation can fix, such as missing business-logic controls.

**Examples:** password reset that relies on easily guessed security questions; a checkout flow without limits allowing unlimited coupon reuse; no rate limit on a sensitive operation; no separation between tenants.

**Prevention:** threat modelling during design (for example STRIDE), secure design patterns, abuse-case and misuse-case stories, security requirements, limits on resource use, and design reviews before coding.

---

### A07: Authentication Failures

**What it is:** Weak or broken mechanisms for proving identity and managing sessions.

**Examples:** permitting weak passwords; no brute-force protection; credential stuffing success; session IDs exposed in URLs; session not regenerated after login; session not invalidated at logout; insecure "forgot password" flow; missing MFA.

**Test:** attempt repeated failed logins in the lab to see if lockout or throttling exists; inspect cookie flags and session ID entropy; check whether the old session survives logout.

**Prevention:** MFA, breached-password checks, rate limiting and lockout, secure session management (new ID at login, expiry, destruction at logout), identical error messages, hardened reset flows, strong password hashing.

---

### A08: Software or Data Integrity Failures

**What it is:** Code or data is trusted without verifying integrity.

**Examples:** auto-updates without signature verification; loading JavaScript from a CDN without Subresource Integrity; insecure deserialisation of untrusted objects; CI/CD pipelines that accept unreviewed changes.

**Prevention:** digital signatures and checksum verification, Subresource Integrity (`integrity` attribute), avoid native deserialisation of untrusted data (use safe formats like JSON with schema validation), code review and protected branches, secure pipelines.

---

### A09: Security Logging & Alerting Failures

**What it is:** Insufficient logging, or logs that nobody monitors, so attacks go unnoticed and investigation is impossible.

**Examples:** failed logins and access denials not logged; logs stored only locally and easily deleted; no alert when thousands of login failures occur; sensitive data written into logs.

**Prevention:** log authentication events, access control failures and input validation failures with timestamp, user and source IP; protect and centralise logs; define alert thresholds and an incident response process; prevent log injection and avoid logging secrets.

---

### A10: Mishandling of Exceptional Conditions

**What it is:** The application behaves insecurely when something unexpected happens: errors, timeouts, resource exhaustion or malformed input.

**Examples:** an error path that skips an authorisation check ("fail open"); detailed stack traces or SQL errors shown to users; unhandled exceptions crashing the service; uncaught edge cases such as null or oversized input; leaving transactions half completed.

**Test:** send malformed, empty, very long or unexpected input and observe the response, error detail and system state.

**Prevention:** fail closed (deny by default on error); catch errors centrally and return generic messages; log details server-side only; set timeouts and resource limits; make multi-step operations transactional; test negative paths.

---

## 2.3 Summary map

| Layer where the flaw lives | Categories |
|---|---|
| Design and architecture | A06 Insecure Design, A03 Supply Chain |
| Identity and access | A01 Broken Access Control, A07 Authentication Failures |
| Data handling | A04 Cryptographic Failures, A05 Injection |
| Platform and operations | A02 Misconfiguration, A09 Logging and Alerting, A10 Exceptional Conditions |
| Trust in code and data | A08 Integrity Failures, A03 Supply Chain |
